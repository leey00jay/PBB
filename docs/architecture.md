# 인지·판단·제어 경계

## 데이터 흐름

```text
센서 / CARLA → adapters → runtime
                           ├─ perception → 인지 결과
                           ├─ planning   → 주행 목표
                           └─ control    → 제어 명령 → adapters → CARLA
```

실행 순서와 import 방향은 다릅니다. 인지 결과를 판단으로 전달하는 것은 `runtime`의 역할입니다.
판단 모듈이 인지 모듈의 구현을 직접 import할 필요는 없습니다.
세 영역은 자기 영역과 `interfaces`에만 의존합니다.
`interfaces`는 다른 `pbb` 패키지에 의존하지 않습니다.
`adapters`는 외부 데이터와 공통 데이터 간 변환을 담당하며 알고리즘을 호출하지 않습니다.
`runtime`은 모든 영역을 연결할 수 있습니다.

## 공통 규격을 먼저 합의

구현 전에 `src/pbb/interfaces/`에서 데이터 클래스를 정의합니다.
아래는 설계 체크 항목이며, 현재 실행 가능한 메시지 API가 정의된 것은 아닙니다.

| 경계 | 합의할 항목 |
| --- | --- |
| 센서 → 인지 | 프레임 ID, 측정 시각, 이미지 형식, 보정값 |
| 인지 → 판단 | 차선/주행 가능 영역, 장애물 위치·속도, 신호 상태, 신뢰도, 유효 여부 |
| 판단 → 제어 | 목표 경로, 목표 속도, 정지 요청, 목표 유효 시각 |
| 제어 → 외부 연동 | 조향, 가속, 제동, 명령 유효 여부 |

단위는 `m`, `s`, `m/s`, 각도는 `rad`를 기본으로 제안합니다.
차량 좌표계의 축과 부호, 시뮬레이션 시간과 실제 시간의 구분, 누락값, 오래된 관측의 처리 방식도 정의해야 합니다.
`carla.Vehicle`, OpenCV 객체 같은 외부 SDK 형식을 공통 메시지 API로 노출하지 않습니다.
공통 규격 변경은 세 영역의 테스트 예제와 함께 먼저 병합합니다.

## 기존 코드 이관 순서

`examples/carla_boundary/`에는 검증한 CARLA 실행 코드와 결과를 보존합니다. `src/pbb`에는 아직 알고리즘을 이관하지 않았으며, 예제 코드를 모듈로 옮길 때 다음 순서를 권장합니다.

1. 실행 환경과 기존 테스트 결과를 기록합니다.
2. 인지 결과·판단 목표·제어 명령의 공통 형식을 먼저 정의합니다.
3. `road_boundary_recovery`의 검출 로직은 `perception`으로 옮기고 기존 입력에 대한 결과를 비교합니다.
4. `boundary_controller.py`의 목표 속도 결정은 `planning`, 조향·종방향 제어는 `control`로 분리합니다.
5. `open_source_autonomy.py` 같은 실행 스크립트의 루프는 `runtime`, CARLA 입출력은 `adapters`로 옮깁니다.
6. 기존 진입점은 필요한 동안 호환용으로 남기고, 시나리오 회귀 테스트를 통과한 뒤 정리합니다.

각 단계는 별도 PR로 진행합니다. 파일 이동만 하는 PR과 알고리즘 동작을 바꾸는 PR을 분리합니다.
서드파티 코드는 출처·라이선스를 함께 보존하고 자체 구현과 구분합니다.

## 기존 작업 브랜치

구조 설정 시 확인한 `ye` 브랜치에는 `decision/decision.py`와
`Docs/Project Plan/decision/decision_design.md`가 있습니다. `yeon`, `yoon` 브랜치도 유지합니다.
이번 구조 설정에는 이 브랜치들의 기능 코드를 병합하지 않습니다.

`ye`의 판단 코드를 통합할 때 구현 위치는 `src/pbb/planning/`으로 맞추고,
기존 `decide()`의 반환 속도가 `km/h`라는 점을 공통 규격에 명시하거나 경계에서 `m/s`로 변환해야 합니다.
import할 때 예제 출력이 실행되지 않도록 예제 실행부를 분리하고,
기존 다섯 입력의 상태·목표 속도를 테스트로 확인한 뒤 별도 PR로 병합합니다.

## 검사 범위

`tests/test_architecture.py`는 정적 import의 모듈 경계를 검사합니다.
절대 import와 상대 import를 모두 검사하며, 핵심 모듈에서 동적 import는 사용하지 않습니다.
이 검사는 데이터 의미·지연·차량 동작을 보장하지 않습니다.
실제 구현을 추가할 때 단위 테스트와 `tests/integration/`의 연결 테스트를 함께 작성해야 합니다.
